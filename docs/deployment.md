# Integrity Test Deployment

## Local Development

Build and run local dependencies plus app containers:

```bash
docker compose -f docker-compose.dev.yml up --build
```

Apply migrations locally:

```bash
cd integrity-tech-backend
DATABASE_URL=postgresql://postgres:localpassword123@localhost:5432/integrity_tech_db?schema=public npx prisma migrate dev
```

Seed local demo data:

```bash
cd integrity-tech-backend
DATABASE_URL=postgresql://postgres:localpassword123@localhost:5432/integrity_tech_db?schema=public npm run seed
```

Run the reproducibility smoke check:

```bash
cd integrity-tech-backend
DATABASE_URL=postgresql://postgres:localpassword123@localhost:5432/integrity_tech_db?schema=public npm run smoke
```

Verify:

```bash
curl http://localhost:3001/health/live
curl http://localhost:3001/health/ready
curl http://localhost:3001/health/dependencies
curl http://localhost:3001/metrics
```

Local private storage is enabled through:

```bash
STORAGE_PROVIDER=local-private
STORAGE_LOCAL_PRIVATE_PATH=.private-storage
```

Snapshots and sensitive files are stored outside `/public` and served only through authenticated endpoints.

## Local Staging

Run production-like local staging:

```bash
docker compose -f docker-compose.staging.yml up --build
```

Apply migrations with production-safe command:

```bash
cd integrity-tech-backend
DATABASE_URL=postgresql://integrity:staging-local-password-change-me@localhost:5432/integrity_staging?schema=public npx prisma migrate deploy
```

Do not use `prisma migrate dev` in staging or production.

The official database bootstrap is the Prisma migration chain. Do not apply `db/schema.sql` as a parallel bootstrap path.

Existing databases that were created before the baseline migration must not run the baseline over already existing tables. Verify the schema first, then mark only the baseline as applied:

```bash
cd integrity-tech-backend
DATABASE_URL=postgresql://... npx prisma migrate resolve --applied 20260701000000_baseline_initial_schema
DATABASE_URL=postgresql://... npx prisma migrate deploy
```

## Private Storage

S3-compatible staging/production configuration example:

```bash
STORAGE_PROVIDER=s3
STORAGE_S3_BUCKET=integrity-production-private
STORAGE_S3_REGION=us-east-1
STORAGE_S3_ENDPOINT=
STORAGE_S3_ACCESS_KEY_ID=from-secret-manager
STORAGE_S3_SECRET_ACCESS_KEY=from-secret-manager
STORAGE_SIGNED_URL_TTL_SECONDS=300
STORAGE_MAX_FILE_BYTES=2097152
```

Sensitive files are accessed through:

```bash
GET /api/files/:fileId
GET /api/files/:fileId/download-url
```

The API validates tenant, owner or staff permission before serving content and never exposes raw object keys to the frontend.

## Production Migration Procedure

1. Confirm backup exists and restore has been tested recently.
2. Review SQL generated by Prisma migration.
3. Run migrations from a controlled job/container:

```bash
npx prisma migrate deploy
```

4. Run `npx prisma validate`.
5. Seed only the approved dataset for the target environment, if required.
6. Run `npm run smoke`.
7. Run `npm run smoke:backup-restore` from an environment that has PostgreSQL client tools.
8. Start one backend instance.
9. Check `/health/ready`.
10. Scale normally only after readiness is green.

## Migration Failure Mitigation

Prisma migrations are forward-only by default. If a migration fails:
- Stop rollout.
- Do not run `migrate dev`.
- Capture migration logs.
- If schema partially changed, decide between:
  - applying a corrective forward migration, or
  - restoring from backup if data integrity is at risk.
- Re-run `npx prisma migrate status` before continuing.

## CI/CD

The GitHub Actions workflow performs:
- backend dependency install
- Prisma validate
- Prisma generate
- backend lint
- backend unit tests
- backend integration tests
- backend build
- backend production dependency audit
- frontend dependency install
- frontend lint
- frontend sync-engine tests
- frontend build
- frontend production dependency audit
- clean PostgreSQL migration deploy from an empty database
- E2E seed
- database smoke validation
- backup/restore smoke validation
- Docker build backend
- Docker build frontend

No cloud deployment is performed automatically yet.

Current audit status:
- Backend has a known moderate transitive vulnerability through `@nestjs/bull -> bull -> uuid` with no direct fix published by npm audit.
- Frontend audit currently requires a major Next.js upgrade to fully resolve reported production advisories.
- CI runs `npm audit --omit=dev` but marks it non-blocking until the dependency remediation phase chooses safe upgrade paths.

## Pre-Production Checklist

- `NODE_ENV=production`.
- `ENABLE_DEV_AUTH=false`.
- `SHOW_SWAGGER=false`.
- `RATE_LIMIT_STORE=redis`.
- `DATABASE_URL` comes from secret manager.
- `REDIS_URL` comes from secret manager.
- `JWT_SECRET` is strong and rotated from demo values.
- `CORS_ORIGINS` contains only approved origins.
- `/health/ready` returns `ready`.
- `/metrics` is reachable only from monitoring infrastructure.
- Private storage is configured and `/health/dependencies` reports storage as `up`.
- Object buckets are private and do not allow public ACLs.
- Database backup and restore procedure has been tested.
- Prisma migrations have been reviewed.
- No `.env` files are baked into images.
